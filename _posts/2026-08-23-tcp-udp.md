## 요약

1. 전송 계층은 프로세스 간 논리적 통신을 제공하고, 다중화/역다중화와 오류 검출은 TCP·UDP 공통이다.

2. 주요 차이는 신뢰성·순서·흐름·혼잡 제어를 누가 책임지느냐이며, TCP는 직접 지고 UDP는 위 계층에 넘긴다.

3. TCP는 손실이 지연보다 치명적인 영역에서, UDP는 지연이 손실보다 치명적인 영역에서 사용된다.

## 전송 계층과 TCP/UDP

### 전송 계층이 하는 일

TCP와 UDP는 모두 전송 계층에 속하는 프로토콜이다. **전송 계층은 서로 다른 호스트의 프로세스 간 논리적 통신을 제공**한다.<br>
여기서 "논리적"이라는 말은, 실제로(물리적으로) 두 프로세스가 직접 연결되어 있지는 않지만 마치 연결되어 있는 것처럼 취급된다는 뜻이다.

전송 계층 아래에 있는 네트워크 계층의 **IP는 best-effort 전달**을 한다. 즉 패킷의 손실, 순서 뒤바뀜, 무결성을 보장하지 않는다.<br>
전송 계층에서는 기본적으로 아래 두 가지를 수행하는데,

- **다중화 / 역다중화**: 소켓에서 나오는 데이터를 모아 헤더를 붙여 세그먼트·데이터그램으로 만들어 네트워크 계층으로 내려보내는 일, 그리고 그 반대.
- **오류 검출**: 체크섬으로 전송 중 비트가 바뀌었는지 확인하는 것.

이때, **신뢰성·순서·흐름 제어·혼잡 제어를 누가 책임지는가에서 TCP와 UDP가 차이**를 보인다. TCP는 이것들을 자신이 책임지고, UDP는 책임지지 않고 위 계층에게 넘긴다.

### 포트와 소켓

포트는 **한 컴퓨터 안에서 프로세스(구체적으로는 소켓)를 구분하는 데 쓰이는 번호**다. 16비트를 사용하므로 0부터 65535까지 표현할 수 있다. 이 중 0~1023번은 well-known port로, 22번은 SSH, 53번은 DNS, 80번은 HTTP처럼 용도가 미리 정해져 있다.

프로세스는 네트워크 통신을 할 때 소켓을 이용한다.<br>
**소켓은 두 프로그램이 네트워크를 통해 데이터를 주고받게 해주는 종단점**이다.<br>
이때, TCP 소켓과 UDP 소켓은 식별 방법이 다르다.

| 구분     | 식별자                                  | 결과                      |
|----------|-----------------------------------------|---------------------------|
| TCP 소켓 | 4-튜플 (출발지 IP·Port, 목적지 IP·Port) | 연결마다 다른 소켓        |
| UDP 소켓 | 2-튜플 (목적지 IP·Port)                 | 출발지가 달라도 같은 소켓 |

## TCP 헤더 구조

TCP 헤더는 기본 20바이트, 옵션을 포함해 최대 60바이트다.

![TCP 헤더 구조](01.png){: w="708" h="403" }

### Sequence number

Sequence number에서 **번호는 세그먼트 단위가 아니라 바이트 단위로 부여**된다.<br>
전송 계층은 위 계층에서 받은 데이터를 MSS(Maximum Segment Size, 한 세그먼트에 실을 수 있는 순수 데이터의 최대 크기) 경계에서 자르고, 잘린 각 묶음에 헤더를 붙이는데, 이때 그 묶음의 첫 번째 바이트 번호가 그 세그먼트의 Sequence number가 된다.

![Sequence number](02.png){: w="685" h="184" }

### Acknowledgment number

Acknowledgment number는 받는 쪽에서 **다음에 받기를 기대하는 바이트 번호**다. TCP는 누적 ACK 방식을 쓰기 때문에, **"지금까지 빠짐없이 받은 바이트의 다음 번호"**를 의미한다.

![Acknowledgment number](03.png){: w="739" h="189" }

### TCP Flag

Flags는 세그먼트의 목적이나 상태를 나타내는 8개의 제어 비트다.

![TCP Flag](04.png){: w="814" h="248" }

## TCP 연결 수립 — 3-way Handshake

TCP는 연결 지향 프로토콜이라서 실제 데이터를 주고받기 전에 **양쪽이 통신 시작을 합의하는 절차**를 거친다. 이것이 3-way handshake다. 이때, 세 번째 단계부터는 실제 데이터를 함께 실어서 보낼 수 있다.

![TCP 연결 수립 — 3-way Handshake](05.png){: w="505" h="355" }

### ISN을 랜덤화하는 이유

- **구 연결의 세그먼트와의 혼동 방지**: ISN을 특정 숫자로 고정하면 예전 연결의 세그먼트가 지금 연결의 것과 섞이고, 서버가 예전 것을 정상 데이터로 받아들일 가능성이 생긴다. 랜덤값으로 설정하면 이 확률이 매우 낮아진다.
- **시퀀스 번호 추측 공격 방지**: ISN이 고정되면 공격자가 Sequence number를 추측해 위조 패킷을 정상 패킷으로 위장해 주입하기 쉬워진다.

### 왜 2-way가 아니라 3-way인가

**지연되어 뒤늦게 도착한 과거의 SYN을 거부하기 위해서**이다.

![왜 2-way가 아니라 3-way인가](06.png){: w="758" h="164" }

- **2-way**: 클라이언트가 이미 연결을 포기한 상태인데 과거의 SYN이 지연되어 지금 도착하면, 서버는 SYN-ACK를 보내는 시점에 연결이 성립됐다고 착각하고 자원을 할당해버린다.
- **3-way**: 같은 상황에서 SYN-ACK를 받은 클라이언트가 마지막 단계에서 RST를 보내고, 서버는 잘못된 연결을 정리할 수 있다.

### SYN Flood와 half-open

3-way handshake의 ② 단계에서 서버는 이미 버퍼와 변수를 할당하고 ACK를 기다린다. 이 상태를 **half-open**이라고 한다. 이 지점을 노린 공격이 **SYN Flood**다.

- 공격자가 출발지 IP를 위조한 SYN을 대량으로 전송.
- 위조된 주소이므로 ③의 ACK가 돌아오지 않음.
- half-open 상태가 계속 쌓여 결국 정상 접속까지 거부.

방어책으로 **SYN 쿠키**가 있다.

- ② 단계에서 자원을 미리 할당하지 않음.
- 연결 정보를 ISN에 암호학적으로 인코딩(해시)해서 전송.
- ③의 ACK가 실제로 돌아오면 그때 검증한 뒤 자원을 할당.

## TCP 4-way 연결 해제

연결을 끊을 때는 4단계를 거친다.

![TCP 4-way 연결 해제](07.png){: w="481" h="453" }

### 왜 3-way가 아니라 4-way인가

②와 ③ 사이에 서버가 **남은 데이터를 마저 보내고, 정상적인 종료를 진행할 시간이 필요**하기 때문이다.<br>
반대로 서버가 보낼 데이터가 없고 바로 종료할 수 있으면, ACK와 FIN을 합쳐서 실제로 3단계로 종료되기도 한다.

### TIME_WAIT이 필요한 이유

마지막 **④ ACK가 유실될 수 있기 때문**이다. 유실되면 서버는 ③ FIN을 재전송하고, 클라이언트는 ACK를 다시 보내야 한다. 이를 위해 클라이언트는 곧바로 CLOSED로 가지 않고 TIME_WAIT에 잠시 머물렀다가 CLOSED로 전환한다.

## TCP 재전송

TCP는 데이터가 잘 도착했는지 확인하는 수단으로 ACK를 쓴다. ACK가 일정 시간 동안 오지 않으면 유실됐다고 판단하고 같은 세그먼트를 다시 보낸다.

### 타임아웃 (RTO)

재전송 기준 시간을 **RTO**라고 하며, 고정값이 아니라 네트워크 상황에 맞춰 동적으로 계산된다.

```text
EstimatedRTT = (1 − α) · EstimatedRTT + α · SampleRTT              α = 0.125
DevRTT       = (1 − β) · DevRTT + β · |SampleRTT − EstimatedRTT|   β = 0.25
TimeoutInterval = EstimatedRTT + 4 · DevRTT
```

- **SampleRTT**: 하나의 세그먼트에 대해 실제로 측정한 왕복 시간.
- **EstimatedRTT**: 기존 추정치에 새 SampleRTT를 반영한 값. 이상치의 영향을 줄이기 위해 α로 가중치를 준다.
- **DevRTT**: 새 SampleRTT가 EstimatedRTT로부터 평균적으로 얼마나 벗어나는지를 나타내는 값. 마찬가지로 β로 이상치의 영향을 줄인다.
- **TimeoutInterval(RTO)**: 추정치에 변동성을 고려한 안전 마진을 더한 값. 권장 초기값은 1초다.

타임아웃이 발생하면 TimeoutInterval을 2배로 늘린다. 단, ACK를 받아 EstimatedRTT가 갱신되면 다시 위 공식으로 재계산한다.

### Fast Retransmit

![Fast Retransmit](08.png){: w="459" h="307" }

수신자는 순서가 어긋난 세그먼트를 받으면 마지막으로 정상 수신한 바이트의 번호를 ACK에 담는다. 그 결과 같은 송신자는 동일한 ACK가 받게 된다.<br>
송신자는 **같은 ACK를 3개 더 받으면** 그 다음 세그먼트가 유실된 것으로 판단하고 타이머 만료 전에 즉시 재전송한다.

**왜 하필 3개인가**

- 네트워크에서는 패킷의 순서가 바뀌어 도착하는 일이 빈번하다.
- 중복 ACK 1개만 받고도 재전송한다면 불필요한 재전송을 남발하게 된다.
- 1개나 2개로는 순서 뒤바뀜과 유실을 구분하기 모호하므로, 여유를 둔 안전 마진으로 3개를 기준으로 둔다.

## UDP 헤더 구조

UDP 헤더는 고정 8바이트다.

![UDP 헤더 구조](09.png)

**UDP 순서·재전송·흐름 제어·혼잡 제어를 하지 않는다**.때문에, TCP와 다르게 아래 필드들이 필요 없다.

- Sequence number / Acknowledgment number
- Receive window / Flags / Options

## Checksum

![Checksum](10.png)

TCP와 UDP(선택적) 모두 오류 검출을 진행한다. 하지만, **TCP는 폐기한 뒤 재전송으로 복구**하지만, **UDP는 폐기하고 끝**이다.

**체크섬이 필요한 이유**는 아래 계층을 신뢰할 수 없기 때문이다. 모든 링크가 오류 검사를 제공한다는 보장이 없고, 라우터 메모리에 저장되어 있는 동안에도 비트 오류가 생길 수 있다.

### Checksum 계산 과정

세그먼트·데이터그램을 워드라는 단위로 나누고, 워드들을 1의 보수 합 방식으로 더한 뒤 비트를 반전시켜 체크섬을 만든다.

**송신자**<br>
① 앞의 두 워드를 더한다.

```text
  0110011001100000
+ 0101010101010101
------------------
  1011101110110101
```

② 세 번째 워드를 더한다. 자리올림이 발생한다.

```text
  1011101110110101
+ 1000111100001100
------------------
 10100101011000001   ← 맨 앞의 1이 자리올림
```

③ 자리올림을 최하위 비트에 되돌려 더한다. (carry wraparound)

```text
  0100101011000001
+                1
------------------
  0100101011000010
```

④ 모든 비트를 뒤집어 체크섬을 만든다.

```text
  0100101011000010
→ 1011010100111101   ← checksum
```

**수신자**<br>
⑤ 받은 워드들과 체크섬까지 전부 더한다.

```text
  0110011001100000
+ 0101010101010101
+ 1000111100001100
+ 1011010100111101   ← 받은 체크섬
------------------
  1111111111111111
```

결과가 **전부 1이면 정상**이고, **0이 하나라도 있으면 오류**로 판단한다.

## UDP 통신 방식 - connectionless / stateless

**UDP에서는 연결 절차가 없다**

![UDP 통신 방식 - connectionless / stateless](11.png){: w="566" h="291" }

**상태를 유지하지 않는다**

![UDP 통신 방식 - connectionless / stateless](12.png){: w="788" h="176" }

UDP 소켓은 목적지 IP·포트만 보고 역다중화하므로, **출발지가 달라도 같은 소켓으로 전달**된다.<br>
송수신 버퍼, 혼잡 제어 파라미터, 시퀀스 번호를 유지하지 않기 때문에 **더 많은 클라이언트를 감당할 수 있다**. 대신 신뢰성이 필요하다면 애플리케이션에서 직접 처리해야 한다(QUIC).

## UDP를 쓰는 이유

- **① 전송 시점의 즉시성**: 애플리케이션이 데이터를 넘기면 즉시 데이터그램으로 만들어 네트워크 계층으로 전달한다.
- **② 연결 설정이 없음**: 설정 지연이 0이다.
- **③ 연결 상태가 없음**: 버퍼·혼잡 제어·시퀀스 파라미터를 유지하지 않아 더 많은 클라이언트를 감당할 수 있다.
- **④ 작은 헤더 오버헤드**: 데이터그램마다 8바이트다. (TCP는 20바이트)

## TCP vs UDP 비교

| 항목          | TCP                              | UDP                                     |
|---------------|----------------------------------|-----------------------------------------|
| 연결 방식     | 연결 지향, 3-way handshake       | 비연결형                                |
| 소켓 식별     | 4-튜플                           | 2-튜플                                  |
| 신뢰성        | O                                | X                                       |
| 순서 보장     | O                                | X                                       |
| 데이터 단위   | 세그먼트                         | 데이터그램                              |
| 헤더 크기     | 20 byte (옵션 포함 최대 60)      | 8 byte 고정                             |
| 흐름 제어     | O                                | X                                       |
| 혼잡 제어     | O                                | X                                       |
| 체크섬        | 필수                             | IPv4 선택 / IPv6 필수                   |
| 서버 자원     | 연결별 상태 유지 필요            | 상태 유지 불필요                        |
| 대표 프로토콜 | HTTP/1.1, HTTP/2, SMTP, SSH, FTP | DNS, DHCP, SNMP, RIP, NTP, QUIC(HTTP/3) |
