## 요약

- FTP는 명령(제어 연결)과 데이터(데이터 연결)를 분리한다.
- 이메일은 보내기(SMTP)와 꺼내오기(POP3 / IMAP)가 분리되어있다. POP3는 내려받고, IMAP는 동기화한다.
- ICMP는 오류 보고와 운영 정보를 전달하여 IP를 보완한다.

## FTP

### FTP의 특징

FTP는 네트워크상에서 호스트(클라이언트–서버) 간에 **파일을 신뢰성 있게 전송**하기 위한 응용 계층 프로토콜이다.

그리고, TCP위에서 동작한다.

RFC 959가 명시한 FTP의 목적은 네 가지다.

- 파일 공유 촉진 (프로그램 · 데이터 파일)
- 원격 컴퓨터의 간접적(프로그램을 통한) 사용 장려
- 호스트 간 파일 저장 방식 차이로부터 사용자 보호
- 신뢰성 있고 효율적인 데이터 전송

FTP의 가장 큰 특징은 하나의 세션을 **제어 연결과 데이터 연결 두 개로 분리**한다는 점이다.

실무적으로 **FTP 자체는 평문 통신 프로토콜**이기 때문에, 어느 모드든 FTP를 쓰는 것 자체를 취약하다고 본다. 꼭 써야 한다면 SFTP나 FTPS 같은 보완된 방식을 사용한다.


### 제어 연결과 데이터 연결

**제어 연결 (control connection)**은 User-PI와 Server-PI 사이에서 **명령(command)과 응답(reply)을 주고받는** 통신 경로이다.

**데이터 연결 (data connection)**은 지정된 모드(mode)와 타입(type)으로 **실제 데이터가 전송**되는 전이중(full-duplex) 연결이다.

![제어 연결과 데이터 연결](01.png){: w="662" h="241" }

연결이 둘로 나뉘어져 있어서 전송 중인 파일도 제어 채널로 인터럽트 메시지를 보내 중단할 수 있다.

제어 연결은 클라이언트가 시작하고, 서버는 포트 21에서 listen한다.

데이터 연결은 **누가 시작하는가에 따라 Active 모드와 Passive 모드**로 갈린다.

중요한 점으로, 서버의 21번 포트만으로는 파일 전송 기능을 쓸 수 없다. **21번으로 만들어지는 것은 제어 연결뿐**이고, 실제 전송은 20번이나 협상 포트로 데이터 연결이 수립되어야 가능하다.


### Active Mode (PORT)

FTP는 기본적으로 Active Mode로 동작한다.

![Active Mode (PORT)](02.png){: w="543" h="414" }

**Active Mode의 문제로 방화벽과 NAT이 있다.** 클라이언트가 인바운드(외부에서 들어오는) 연결을 받으려면 자기 네트워크의 방화벽·NAT을 직접 설정해야 하는데(포트포워딩 등), 현실적으로 클라이언트가 이 작업을 할 수 있는 경우는 매우 제한적이다.

- 외부(서버)에서 들어오는 연결 → 클라이언트 방화벽이 차단
- 패킷 필터 방화벽은 '임의 포트로 들어오는 호출'을 허용할 수 없음
- 외부(서버)에서 NAT 뒤의 사설 IP로는 접근 자체가 불가능


### Passive Mode (PASV)

Passive Mode는 이러한 부담을 서버가 지도록 설계되었다.

![Passive Mode (PASV)](03.png){: w="544" h="420" }

이러면 **클라이언트 방화벽의 부담이 사라진다.** 새 연결을 시작할 수 있는 것은 ACK 비트가 없는 최초 SYN뿐이므로, 방화벽 필터는 이것을 '밖으로 나가는 방향'만 허용하도록 간단히 설정할 수 있다.

- ACK 없는 SYN이 안으로 들어옴 → 새 연결을 시도하는 것 → 차단
- ACK 없는 SYN이 밖으로 나감 → 우리 쪽에서 새 연결을 여는 것 → 허용
- ACK가 붙은 패킷(진행 중인 연결의 후속 패킷) → 방향 상관없이 통과

**대신 서버 쪽에 부담이 생긴다.** 클라이언트가 거는 새 연결(SYN)이 안으로 들어올 수 있도록 관리자가 방화벽을 설정해야 하는데, PASV 응답의 포트는 매 세션마다 랜덤하게 결정되므로 넓은 포트 범위를 개방해야 한다.

## 이메일 프로토콜

### 전체 흐름

이메일은 보내는 SMTP와 '꺼내오는 POP3·IMAP로 분리 되어있다.

![전체 흐름](04.png)

이때, **송신은 송신자가 메일 서버로** **메일을 보내는 과정으로 SMTP가 사용**되고, **수신은 메일 서버에서 수신자에게메일이 가는 과정으로 POP3 또는 IMAP가 사용**된다.


### SMTP

**메일을 서버로 밀어 넣는(push) 전송 전용 프로토콜**이다.

사용되는 포트는 다음과 같다.

- **25**: MTA(서버) 간 릴레이
- 587: 클라이언트 제출 (STARTTLS)
- 465: 클라이언트 제출 (Implicit TLS)

전송 절차는 세 단계이다.

- MAIL FROM: 발신 봉투 주소를 서버에 알림
- RCPT TO: 수신자 지정
- DATA: 이제 본문을 보내겠다는 신호 전달


### POP3

**서버 메일함에서 메일을 내려받는 단순 수신 프로토콜**이다. 목록·수신·삭제 세 가지 동작을 제공한다.

사용되는 포트는 다음과 같다.

- **110**: 평문 (또는 STLS)
- 995: POP3S (Implicit TLS)

기본 동작은 접속 → 전부 다운로드 → 서버에서 삭제 → 오프라인에서 읽기다.

**서버 부담이 적고 구현이 단순**한 대신, **여러 기기 간 상태 공유가 불가능**하다는 장단점이 있다.

보안 관점에서, 계정 탈취 시 서버엔 원본이 없어 피해가 제한적이다.

운영·관리 관점에서, 기기 장애 시 메일 유실 위험이 있고 백업을 사용자가 관리해야한다.


### IMAP

**메일을 서버에 두고 원격 메일함을 로컬 폴더처럼 관리하는 접근 프로토콜**이다. 폴더 구조·읽음/답장/삭제 플래그·검색을 모두 서버가 관리한다.

사용되는 포트는 다음과 같다.

- **143**: 평문 (또는 STARTTLS)
- 993: IMAPS (Implicit TLS)

PC·스마트폰·웹 **어디서 봐도 같은 상태가 유지**된다. 대신 프로토콜이 복잡하고 서버의 저장·색인·검색 부담이 커서 **메일함당 부하, 관리 비용 등이 높다**.

보안 관점에서, 계정 탈취 시 전체 메일함이 노출되는 위험이 있다.

운영·관리 관점에서, 서버 측 백업 정책으로 일괄 관리가 가능하다.

요즘 대부분의 메일 서비스는 관리 부담이 있어도 효율성 측면이 더 중요하기 때문에 IMAP로 메일 서버를 운영한다. POP3를 쓰는 곳은 내부 기밀을 매우 중요하게 여기거나 메일 접근을 크게 제한하는 환경 정도다.

## ICMP

### ICMP의 특징

IP의 보조 프로토콜로, 라우터와 호스트가 **오류 보고와 운영 정보를 전달**하는 데 사용된다. 실질적으로 IP의 일부이며 모든 IP 모듈이 반드시 구현한다.

IP는 신뢰성 없는(best-effort) 프로토콜이기 때문에 처리 중 오류를 보고할 책임을 가진 ICMP가 만들어졌다. 이때, 오류를 고치지는 않는다.

![ICMP의 특징](05.png){: w="360" h="341" }

메시지는 크게 두 종류이다.

- **질의(Query)**:
  - 호스트·라우터의 생존 여부나 상태를 확인하는 메시지
  - 예시) ping. Type 8(Echo Request)/ Type 0(Echo Reply) 등
- **오류 보고(Error)**:
  - IP 패킷을 처리하다 문제가 생겼을 때 그 원인을 알리는 메시지
  - 예시) Type 3(목적지 도달 불가), 5(리다이렉트), 11(시간 초과), 12(파라미터 문제) 등  

오류 메시지가 오류 메시지를 부를 수 있기 때문에, 무한 재귀를 막는 규칙이 있다.

- ICMP 오류 메시지에 대해서는 ICMP를 보내지 않는다.
- 단편화된 패킷은 fragment 0(쪼개진 패킷의 첫 조각)에 대해서만 오류를 보낸다.

실무에서는 ping(호스트 응답 및 RTT 확인)과 traceroute(패킷 경로 및 각 구간 지연 확인)로 활용한다.

그러나, 살아있는 호스트 스캔이나 DoS 등 공격에 악용되기도 하므로 보안 정책상 차단될 수 있다.


### Destination Unreachable (Type 3) - 목적지 도달 불가

**패킷이 목적지에 도달할 수 없을 때, 문제를 발견한 라우터 또는 호스트가 송신자에게 보내는 메시지**이다.

### Redirect (Type 5) - 더 나은 경로 안내

**송신 호스트가 비효율적인 게이트웨이로 패킷을 보냈을 때, 라우터가 "이 목적지는 다른 게이트웨이가 더 적절하다"고 알려 경로 설정을 최적화하도록 유도하는 메시지**이다.

![Redirect (Type 5) - 더 나은 경로 안내](07.png)

<tr><td>1</td><td>Redirect for Host</td><td>해당 호스트만 다른 게이트웨이로 보내라</td></tr>

### Time Exceeded (Type 11) - 시간 초과

**패킷이 시간 제한을 초과해 폐기되었음을 송신자에게 알리는 메시지**이다.

![Time Exceeded (Type 11) - 시간 초과](08.png)

traceroute는 이 메시지를 이용한 도구다. TTL을 1부터 늘려가며 패킷을 보내고, 각 라우터가 반환하는 Time Exceeded 메시지의 출발지 주소로 경로상의 홉을 순서대로 파악한다.

  
Code 별 세부 원인은 다음과 같다.

<tr><td>1</td><td>Reassembly time exceeded</td><td>단편화된 조각의 재조립 시간 초과</td></tr>
